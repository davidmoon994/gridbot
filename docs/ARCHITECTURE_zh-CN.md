# GridBot 架构设计文档

## 1. 设计来源

本项目参考了 [NOFX](https://github.com/NoFxAiOS/nofx) 的两条核心设计思想，并将其中"AI 决策"的部分替换为经典的**移动网格算法**：

1. **决策层与执行层解耦**：策略（这里是网格引擎）只负责"提议要挂什么单"，不直接触碰交易所；
2. **风控在代码层强制执行**：所有下单请求必须经过独立的风控引擎校验，策略参数无法绕开这一层。这是 NOFX 文档中反复强调的"硬约束"思路——即使决策层出错，也有最后一道防线。

NOFX 原本用 AI 模型做决策、Go 做风控和执行；本项目把决策层换成不依赖 AI、完全确定性的移动网格算法，同时保留"Web 配置 + 数据库持久化 + 实时控制"的产品形态。

## 3. 移动网格算法

### 3.1 与传统固定网格的区别

传统网格机器人的做法是：开仓时选定一个价格区间，均分成 N 格，价格在区间内震荡时低买高卖。缺点很明显——一旦价格突破区间进入单边趋势，网格要么被套在顶部空仓等回调，要么在底部持续加仓被深套。

移动网格做两个改进：

| 维度 | 传统固定网格 | 本项目的移动网格 |
|---|---|---|
| 网格中心 | 开仓时固定 | 跟随 EMA 移动（`strategy.LastEMA`） |
| 网格间距 | 固定百分比 | 按 ATR 动态计算，波动大间距变宽（`strategy.ATR`） |
| 趋势应对 | 无 | 价格偏离中心超过阈值格数时自动撤单重建（Recenter） |

### 3.2 核心参数说明（对应 `strategy.Config`）

- `GridCount`：中心线上下各布多少层网格
- `EMAPeriod` / `ATRPeriod`：计算中心和间距用的K线周期数
- `ATRSpacingMultiplier`：间距 = ATR × 该系数，数值越大网格越宽
- `MinSpacingPercent` / `MaxSpacingPercent`：间距的百分比上下限（防止极端行情下间距失控）
- `RecenterThresholdGrids`：价格偏离中心超过多少"格"触发重新居中
- `MinRecenterIntervalSec`：两次重新居中的最小间隔，防止价格在边界反复抖动导致频繁重建
- `Mode`：`long_only`（只做多，稳健）或 `neutral`（双向，高位开空低位开多，收益更高但风险也更高）
- `MaxTotalPositionQuote`：策略自身设定的仓位预算（风控引擎会做独立的二次校验）

### 3.3 运行流程（`strategy.Engine.OnTick`）

1. 检查所有挂单是否已成交（通过对比交易所返回的"当前挂单列表"与本地记录）；
2. 对新成交的层，在相邻层挂出配对的止盈单（`onLevelFilled`）；
3. 判断价格偏离中心是否超过阈值，若是则重新居中（撤销未成交挂单，围绕新 EMA 中心和新 ATR 间距重建网格，同时把仍持仓的层迁移到新网格里最近的位置，避免丢失仓位跟踪）；
4. 补齐所有缺失的挂单。

### 3.4 已知简化点（生产化前需要注意）

- 订单成交判定用"从挂单列表消失"来简化推断，生产环境建议改为查询订单状态区分"成交"与"被动撤销"；
- `neutral` 模式下的双向持仓在多数交易所需要"双向持仓模式"支持（如 Binance 合约的 Hedge Mode），请确认交易所账户已开启；
- 强平保护（`risk.Engine.ShouldForceClose`）目前只记录事件，没有自动下达平仓单，需要你在 `manager.tick` 中按需接入。

## 4. 风控引擎（硬约束，策略无法覆盖）

对应 `risk.Engine` + `risk.GuardedExchange`：

- 用**装饰器模式**包装交易所接口：任何策略代码调用 `PlaceOrder`，实际执行的是 `GuardedExchange.PlaceOrder`，内部先做风控裁决（`Engine.Evaluate`），拒绝就直接返回错误，不会到达真实交易所；
- 硬约束项：最大杠杆、单交易对仓位占净值比例、总保证金使用率、最小订单金额、当日最大亏损熔断、极端行情（插针）自动熔断；
- 回撤保护（`ShouldForceClose`）：某个持仓的浮盈从历史峰值回撤超过设定比例时触发提醒/强平。

这套设计的核心价值：**即使你在 Web 界面上把网格参数配置错了（比如把每格金额设成账户全部余额），风控引擎依然会在下单前拦截，不会让错误配置直接爆仓**。

## 5. 可插拔的交易所接入

`exchange.Exchange` 是唯一需要实现的接口（见 `exchange/exchange.go`）。已提供：

- `PaperExchange`：内存模拟盘，随机游走驱动行情，可直接体验完整流程，无需任何 API Key；
- `BinanceFuturesExchange`：Binance U本位合约的**骨架**，方法签名齐全，内部标注了需要实现的 REST 端点和签名方式（HMAC-SHA256），因为本沙箱环境网络无法访问交易所域名，具体请求代码需要你在有网络权限的环境里补充。

接入 OKX / Bybit 等其他交易所，只需新建一个实现了 `Exchange` 接口的 struct，`strategy`、`risk`、`manager`、`server` 层完全不需要改动。

## 6. 数据持久化

`store` 包基于 SQLite（`github.com/mattn/go-sqlite3`，CGO 驱动），三张表：

- `grid_configs`：每个交易对当前的网格配置和启用状态，程序重启时会自动读取并恢复运行（见 `main.go` 的 `restoreGrids`）；
- `events`：所有网格成交、止盈、重新居中、风控拒单、错误事件的日志；
- `pnl_history`：定期记录的已实现盈亏与总持仓快照，用于绘制历史曲线。

## 7. Web 控制台

`server` 包用 Go 1.22 内置的 `net/http.ServeMux`（支持路径参数和方法匹配，无需引入第三方路由库）暴露 REST API，静态页面通过 `go:embed` 打包进二进制，部署时只需一个可执行文件 + 配置文件。

前端是单文件原生 HTML/CSS/JS（无构建步骤），每 3 秒轮询一次 API，展示：网格结构（价格阶梯图，区分买/卖/持仓状态）、账户余额、已实现盈亏、事件日志、启动/停止控制。

## 8. 认证与交易所凭证管理（2026-08 新增）

### 9.1 登录认证

`auth` 包实现了最简单直接的单管理员账户认证，只用标准库（不引入 bcrypt 等第三方加密库）：

- 首次访问自动跳转 `/setup.html` 创建管理账户（用户名+密码，只能创建一次）；
- 之后访问任何页面/API 都需要登录（`/login.html`），由 `server.authGate` 中间件统一拦截：
  - 没有账户 → 强制跳转 `/setup.html`（API 请求返回 401）
  - 有账户但未登录 → 强制跳转 `/login.html`（API 请求返回 401）
  - 已登录 → 放行
- 密码用随机盐 + 10 万轮 HMAC-SHA256 迭代存储；会话令牌保存在服务进程内存中，重启后需要重新登录。

### 9.2 交易所凭证绑定/解绑

币安、OKX 的 API Key/Secret（以及 OKX 的 Passphrase）不再写在配置文件或代码里，
而是通过 Web 控制台的"交易所账号"面板运行时绑定，保存在 SQLite 的
`exchange_credentials` 表中：

- **绑定**：`POST /api/exchanges`，保存凭证后会立即尝试连接（拉一次余额做连通性测试），
  成功则切换为当前生效交易所并记录到 `active_exchange` 表，下次启动自动恢复连接；
  失败则凭证仍会保存，但不会切换过去，避免误填 Key 后策略跑在一个连不上的交易所上。
- **解绑**：`DELETE /api/exchanges/{type}`，删除凭证；如果这是当前使用中的交易所，
  自动退回内置模拟盘（不会自动撤单/平仓，解绑前请自行确认没有未处理的仓位）。
- **切换**：`POST /api/exchanges/{type}/activate`，激活一个此前已绑定过的交易所，
  不需要重新输入 Key。

`manager.Manager` 因此改造为支持运行时热切换交易所（`SetExchange` 方法）：
切换时会先停止所有正在运行的网格（避免旧交易所的挂单/仓位在切换后失去追踪），
再替换底层交易所实例——`risk.GuardedExchange` 的账户状态查询函数通过方法调用
（而非闭包捕获变量）动态读取当前交易所，因此风控引擎在切换后立刻对新交易所生效。

### 9.3 OKX 适配器

新增 `exchange/okx.go`，实现 OKX V5 永续合约的完整对接。与 Binance 的关键差异：

- **签名方式**不同：`base64(HMAC-SHA256(secret, timestamp+method+requestPath+body))`；
- **交易对命名**不同：OKX 用 `BTC-USDC-SWAP` 这种带连字符的 instId，代码里做了
  通用符号（`BTCUSDC`）到 instId 的双向转换；
- **下单单位**不同：OKX 永续合约按"张"下单，需要用 `ctVal`（每张合约对应的
  标的币数量）做换算，`PlaceOrder`/`GetPositions` 里都做了相应转换；
- **没有独立测试网域名**，用同一域名 + 请求头 `x-simulated-trading: 1` 进入模拟交易。

## 9. 2026-08 稳定性修复

上线前排查发现并修复了以下几个真实问题，均已通过白盒测试验证（`manager/manager_smoke_test.go`）：

### 9.1 极端行情熔断此前完全不会触发

`risk.Engine.Evaluate` 里的极端行情检测代码只在网格引擎恰好有新订单要下的时候才会
被执行到——如果价格暴涨/暴跌的那个tick周期里网格没有触发任何新挂单（比如所有该挂
的单子都已经挂着），检测代码根本不会跑，熔断形同虚设。

修复：新增 `risk.Engine.CheckPriceMove(lastPrice, prevPrice)`，由 `manager.tick()`
在**每个**tick周期都主动调用一次，不再依赖"这个周期是否恰好有下单动作"。`Evaluate`
内部仍保留一次调用作为兜底。

同时修复了一个更基础的数据错误：`manager.buildAccountState` 此前把 `PrevPrice` 和
`LastPrice` 都设成同一个当前价格——自己和自己比较，波动永远是0，检测逻辑即使被调用
到也不可能触发。现在 `Trader.lastPrice` 会在每个tick结束时更新为"当次观察到的价格"，
下一个tick用它作为真正的"上一次价格"参与比较。

### 9.2 挂单成交/撤销误判

此前用"这个单子是否还在交易所的挂单列表里"来判断是否成交——但手动撤单、被交易所
拒绝的订单也会从挂单列表消失，会被误判成"已成交"，进而错误地认为持有仓位并挂出
不存在的止盈单，导致仓位跟踪彻底错乱。

修复：`strategy.Level` 新增 `ExchangeOrderID` 字段，`OnTick` 发现某个挂单从列表消失后，
改为调用 `GetOrder` 查询该订单的真实状态，只有 `Filled` 才按成交处理，`Canceled`/
`Rejected` 会把该层重置为空层，其余状态保持原样、下次tick重试。

### 9.3 强平保护此前只记日志，不会真的平仓

`risk.Engine.ShouldForceClose` 触发后，`manager.tick()` 此前只是写一条事件日志，
并不会真正对交易所下单。现在会对触发回撤保护的那个方向下达市价 `ReduceOnly` 平仓单。

同时把浮盈峰值的追踪粒度从"每个交易对一个峰值"改成"每个交易对+持仓方向一个峰值"
（`Trader.peakPnLPct` 从 `float64` 改成 `map[exchange.PositionSide]float64`）——
neutral模式下多空仓位的浮盈走势相互独立，共用一个峰值会导致误判。

强平下单成功后会调用新增的 `strategy.Engine.ForceReset`，撤销该交易对所有剩余挂单
并清空引擎内部状态，下一次tick会重新初始化整个网格——因为强平是绕过网格引擎自身
状态机、直接对交易所下的单，引擎内部记录的挂单/持仓状态已经和交易所真实状态不一致，
与其尝试精细修补，整体重置是能保证状态一致性最简单可靠的做法。

### 9.4 当日亏损熔断此前恒为0

`risk.Limits.MaxDailyLossQuote` 这项熔断配置此前完全没有实际数据支撑——
`DailyRealizedPnL` 在代码里是硬编码的 `0`。

修复：`Trader` 新增 `dailyBaselinePnL`/`dailyBaselineDate` 字段，每天第一次tick
（必须在调用 `engine.OnTick` **之前**完成，因为 `OnTick` 内部下单会触发风控校验）
把当时的累计已实现盈亏记为当日基准，之后 `当前累计已实现盈亏 - 基准` 就是当日盈亏，
供风控引擎判断是否触发每日熔断。

### 9.5 拼写错误的交易对会无限重试、刷错误日志

新增连续失败计数器（`Trader.consecutiveErrors`），达到 `maxConsecutiveErrors`（5次）
后自动调用 `StopGrid` 停止该网格，并记录一条 `auto_paused` 事件说明原因，避免无人
值守时因为交易对拼写错误、凭证失效等问题一直空转刷日志。

### 9.6 明文HTTP的风险提示与可选HTTPS

`config.AppConfig` 新增 `TLSCertFile`/`TLSKeyFile`，两者都配置时用
`http.ListenAndServeTLS` 提供 HTTPS 服务；否则如果监听地址不是明显的"仅本机可访问"
（`127.0.0.1:`/`localhost:`/`[::1]:` 开头），启动时会打印醒目警告。

同时修正了一个更根本的问题：`config.Default()` 此前的默认监听地址是 `":3000"`——
这实际上监听的是**所有网卡**，局域网内其他设备都能连上，而不是只有本机。默认值
已改为 `"127.0.0.1:3000"`。

## 10. 现货交易支持（2026-08 新增）

### 10.1 现货与合约的核心差异

| | 合约 | 现货 |
|---|---|---|
| 杠杆/保证金/强平价 | 有 | 无（`Leverage` 固定视为1） |
| 做空 | 支持（`neutral`模式） | 不支持——只能先买后卖 |
| 交易所原生"持仓"查询 | 有（`GetPositions`） | 无，只有钱包余额 |

`long_only` 网格模式（低位买入、高位卖出止盈，不做空）本身就完全符合现货的
交易语义，不需要改策略逻辑本身；真正需要改造的是"网格模式与市场类型的合法性
校验"和"没有交易所原生持仓可查时怎么喂给风控引擎"这两点。

### 10.2 `neutral` 模式在现货下的拦截

`strategy.Config` 新增 `MarketType`字段（`"spot"` | `"futures"`）和 `Validate()`
方法：现货 + `neutral`（会开空）是一个在真实交易所必然失败的非法组合，
`manager.StartGrid` 会在启动网格、发起任何真实下单之前就用当前实际生效的
交易所类型校正 `MarketType` 并调用 `Validate()`，拒绝这种非法组合——
不会等到用户配置完、真下单时才在交易所侧报错。

Web 界面上选择现货交易所后，"新建网格策略"表单也会自动把模式锁定为
"只做多"、杠杆锁定为1（对应 `applySpotUIConstraints`），但这只是 UX 层面
的提示，真正的强制校验在服务端。

### 10.3 现货没有交易所原生持仓——manager 改用网格引擎自己的记账

现货交易所的 `GetPositions` 固定返回空列表（`BinanceSpotExchange`/
`OKXExchange`（SPOT模式）都是如此）。原因：现货钱包里的某个资产余额，
可能不全是这个网格买入的（用户可能本来就持有），直接拿钱包余额当"这个网格的
持仓"来做风控计算是错的。

`strategy.Engine` 新增 `PositionSummary()` 方法，汇总所有"已成交未平仓"的
多头网格层，算出这个网格自己实际买入、还没卖出的数量和加权平均成本价。
`manager.currentPositions()` 是这两种数据来源的统一入口：判断当前交易所是否
现货（`IsSpotExchange()`，通过交易所标识是否以 `_spot` 结尾判断），现货就用
`PositionSummary()` 合成一个虚拟持仓（`PositionSide`固定为多头，`Leverage`固定为1），
合约就照常查询交易所真实持仓。仓位占比校验、浮盈峰值追踪、回撤强平保护
这几处原本直接调用 `exchange.GetPositions()` 的地方都统一改走这个入口，
现货和合约共用同一套风控判断逻辑。

### 10.4 OKX 现货复用同一个适配器

OKX 现货和合约的签名方式、账户/交易接口结构高度相似，没有另建 `okx_spot.go`，
而是给 `OKXExchange` 加了 `MarketType` 字段（`"SWAP"` 默认 / `"SPOT"`），
`NewOKXSpotExchange` 只是 `NewOKXExchange` 之上多设一个字段的语法糖。
主要差异点在这几处：
- `instId` 格式：合约 `BTC-USDC-SWAP`，现货 `BTC-USDC`（无后缀）；
- 合约下单单位是"张"（需要 `ctVal` 换算成实际币数量），现货直接就是币数量——
  这里统一处理：现货的 `ctVal` 固定设为1，两种模式复用同一套张数/币数量换算代码，
  不用写两份；
- 下单参数 `tdMode`：现货是 `"cash"`，合约是 `"cross"`/`"isolated"`；
- **一个容易踩的坑**：OKX 现货市价买单的 `sz` 默认表示"花了多少计价货币"，
  不是"买了多少标的币"，跟我们内部统一的 Quantity 语义（永远是标的币数量）
  不一致，必须显式传 `tgtCcy: "base_ccy"` 才能让 `sz` 按标的币数量理解。

币安现货则是完全独立的 `exchange/binance_spot.go`，因为币安现货和合约用的
是不同域名（`api.binance.com` vs `fapi.binance.com`）和不完全相同的字段命名
（比如最小名义价值过滤器，现货较新版本叫 `NOTIONAL`，合约是 `MIN_NOTIONAL`），
没有 OKX 那样能直接复用大部分代码的条件，分开实现更清晰。
